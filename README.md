# ARC Prize 2026 / ARC-AGI-3 攻关记录

> **TL;DR (English)** — Complete, reproducible 100.00 (perfect) scores on **two** public
> ARC-AGI-3 environments: `ls20` (7 levels, 335 actions vs. human 776) and `tr87`
> (6 levels, 127 actions vs. human 414), every level hitting the 115% per-level cap.
> What made it work, what it cost, and — more usefully — **where the approach stops
> working**, measured against all 25 public environments. The honest headline: the
> planning/search engine generalizes further than expected (`tr87` was first written
> off as search-proof, then cracked), but the perception layer does not, and every
> rule was still induced by a human.

在 ARC-AGI-3 的公开环境 `ls20`(七关)和 `tr87`(六关)上分别拿到满分,并把方法和它的边界都记下来。

这个仓库的价值不在那个满分——**它更有用的部分是后半段:方法在什么地方失效,以及为什么。**

## 二、方法

整条流水线是:**帧差分感知 → 行走采样建模 → 模型上规划 → 真机逐步验证**。
完整方法论在 [`notes/pipeline-playbook.md`](notes/pipeline-playbook.md),这里只讲三个决定成败的点。

### 1. 搜索状态必须是语义态,不能是整帧像素

整帧里有递减的能量条和走动的巡逻体,**同一个位置在不同步数下永远哈希不相等**,去重直接失效,BFS 退化成穷举(实测内存吃到 4GB,深度 40 未解)。

换成 `(格, 形状, 颜色, 能量)` 四元组后,状态空间从天文数字压到十万量级。同深度 20 的前沿对比:整帧 1307 → 掩掉 HUD 542 → 语义态 477,且增速平缓。

### 2. 启发式必须有梯度

L6 末段卡了很久。同一份搜索代码,只换 `h`:

| 启发式 | 结果 |
| --- | --- |
| 格距 + 形状不对罚 6 + 颜色不对罚 4 | 2 万次扩展,`h` 在 11~24 反复横跳,未解 |
| **离线模型上到目标的真实剩余步数** | **6 秒解出**,`h` 从 44 单调降到 0 |

常数罚项没有梯度——"差一次旋转"和"差三次旋转加换族"同分,最佳优先立刻退化成广度搜索。

正确做法:在离线转移图上枚举可达的 `(格,形状,颜色)`(L6 共 6196 态),建反图,从目标反向 BFS 得精确距离表。它忽略能量约束所以是下界(可采纳),真机只在移动机关处偏离。

**一句话:真机负责"走得通不通",离线模型负责"该往哪走"。** 两者分工比各自单干都强。

### 3. 分段求解:把一次深指数拆成两次浅指数

L7 单段 BFS 要摸到深度 60+ 才可能通关。拆开之后**第一个候选就通了**:

- 阶段 1:BFS 到任意位置上的 `(目标形状, 目标颜色)` —— 深度 42 命中
- 阶段 2:从该状态继续 BFS 到通关,**丢弃任何改变形状或颜色的转移**
- 阶段 2 只扩展了 342 次

原因很直白:形状颜色冻死之后,分支因子从 4 降到接近 1,搜索退化成纯导航。
**先把配置维度配好、再冻住它去导航,比让搜索同时优化位置和配置便宜一个数量级。**

### 4. 漏解可以,错解不行

所有状态转移都在真模拟器上实走(`clone` + `perform_action(raw=True)`)。语义去重会合并巡逻体相位不同的状态,**可能漏解**;但因为每一步都被真实执行过,**找到的路径按构造即已验证**,绝不会输出无效解。

这个方向性在评测场景里必须守住。

## 三、方法的边界(这部分比满分重要)

拿到满分之后,我把全部 25 个公开环境(183 关)下载下来做迁移测试。结论比预期悲观得多。

### 1. 动作空间就先卡掉九成

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| 纯 `[1,2,3,4]` | **2**(`ls20`, `tr87`) | 本方案的 BFS 分支因子为 4 |
| 其他 keyboard | 3 | 含 ACTION5/7 |
| 含 click(ACTION6) | 19 | 每步要从 **64×64 = 4096 个坐标**里选一个 |

click 类游戏每步 4096 个分支,穷举式搜索在那里直接不成立。

### 2. 表面结构可以毫无共通

`tr87` 是另一个纯方向键游戏,但它**根本不是移动游戏**:没有玩家、没有地图。ACTION3/4 移动光标,ACTION1/2 切换当前位的符号,要把一串符号调成正确答案。

`ls20` 那套感知层(玩家块检测、能量条读数、锁解码)**一行都用不上**——tr87 的感知层
(框检测、5×5 符号提取、光标定位)是从零重写的。

深层结构倒是一样的——都是"调节一个可编辑状态直到匹配目标"——但这个共性落不到共享代码上。

### 3. "反馈密度是分水岭"是个被自己推翻的判断

最初的结论是:`tr87` 实测没有任何中间反馈(枚举一位的 7 种符号,画面除该位自身零像素
变化),全对才过关,盲搜 7⁵ 而人类基准 54 步——"搜索在这里不是慢,是没有方向"。

**这个判断错了,后来 `tr87` 被打到满分**(全程见 [`notes/tr87-playbook.md`](notes/tr87-playbook.md))。错在漏算了两件事:

- **"无反馈"只对真实环境成立**。`clone` 里试错免费、不计入动作分母,而"全对即过关"
  这个判定在克隆世界里就是密集反馈。7⁵~7⁷ 的克隆树穷举只要几分钟,真机只走最短
  按键序列——这直接吃掉前四关。
- **穷举撑不住的规模(L5 的 7⁸、L6 的 7¹²),靠前四关穷举攒下的 ground truth 逆向
  出规则再攻**:变换等价类匹配 + 结构化谓词把 L6 的 138 亿组合剪到 2352 个候选。

修正后的边界:真正卡死搜索的不是反馈密度,是**克隆试错的组合规模**与**规则归纳的
自动化**——前者有明确的位数红线(每加一位 ×7),后者见下一条。

### 4. 最关键的一条:所有规则都是人推出来的

颜色是第二个匹配维度、锁的 3×3 编码规则、旋转器是会移动的巡逻体、补给一次性、L7 视口会滚动——**这些全部来自人工推理,不是程序发现的**。`tr87` 同样:切分结构、变换等价类、答案的回文布局,每一条都是人看着 ground truth 归纳的。

而比赛要求这些必须由程序在断网的开源小模型上自动完成,且每一步试探都计入分母。

这一条已经用官方代码核实过,不是推测:Milestone 1 冠军 Tufa Labs 的 Kaggle 提交 notebook 里,竞赛模式构建游戏列表时传的是 `environments_dir=""`——**真实评测跑的时候本地一个游戏源码都没有**,连有哪些游戏都得问服务端要。同时 `competition_arcade.py` 写明竞赛约束包含 **hidden baselines**,也就是赛时你连自己得多少分都算不出来。

所以这个仓库证明的是:**给定正确的规则理解,规划与验证引擎足够强**。
它没有证明的是:**能不能自己得到那个理解**。后者才是 ARC 的核心命题。

## 四、六个踩过的坑

每一条都真实付出过代价,按吃亏程度排序。

1. **两个事件共享同一表面特征时,别用该特征区分。** 死亡和捡补给都让能量上升,于是学习器把"关卡起点"记成了补给点,规划器一直往一个不存在的补给跑。正解是看位置——死亡会传送回起点,捡补给是正常移动一格。修正后死亡次数从 174 降到 65。

2. **判断"搜不出来"是深度不够还是机制没摸清,别靠加深搜索去试。** L7 盲搜到深度 48 只长出 24 种形状、看不到目标形状,我一度判定它不可达;改跑一个只回答"形状可达集有多大、机关映射是什么"的诊断脚本,才发现目标就在深度 41。**一个只回答"机制是什么"的诊断跑,比多搜十层都值钱。**

3. **对象汤式引擎不能做部分快照。** camera / interface 与 game 有交叉引用,部分复制必然导致状态泄漏(实测能量条区域可见地错乱)。只能整对象单 memo 深拷贝。验证分叉回滚要用"存档 → 走岔路 → 读档 → 续走 vs 一路直通"逐帧比对。

4. **打印 diff 时的 top-N 截断会掩盖第二个移动体**,据此得出的结论全错。

5. **核账脚本自身会重复计数。** L5 的解合并进主档后,计分脚本又追加了一次,总步数虚高 29% 而其他数字全部合理。

6. **搜索内通关 ≠ 解可复现。** L6 拼接分段解时,`leg1` 是执行完穿锁动作**之后**取的快照(已含那一步),代码又补了一次,多出的一格让后面 48 步全部错位——搜索进程内打印"通关",全新环境重放却在中途饿死。**只有整条重放才算数。**

另外,读框对齐这种事,人做都会错:分析 `tr87` 时我把映射表的边框读偏了一列(框是列 22-28,内部该取 23-27,取成了 24-28),导致映射出的符号跟实际可选符号完全对不上,差点得出"映射表是假的"这种错误结论。程序自动做只会更难。

## 五、复现

```bash
# 依赖(uv 管理)
uv sync

# 需要自己的 ARC API key,写进 .env(该文件已被 .gitignore 排除)
echo "ARC_API_KEY=你的key" > .env

# 下载环境(SDK 会拉到 environment_files/,该目录不随仓库分发)
uv run python fetch_games.py ls20

# 终验两个满分解
OPERATION_MODE=OFFLINE uv run python score.py       # ls20
OPERATION_MODE=OFFLINE uv run python score_tr87.py  # tr87 (需先 fetch_games.py tr87)
```

`OPERATION_MODE=OFFLINE` 让 toolkit 完全不联网。在有网络限制的环境下,这一条能把每次 `make` 从等 SSL 超时变成秒回。

## 七、AI 实际看到的输入

值得单独说一下,因为这决定了任务难度。

每一步的观测就是一张 **64×64 的整数网格**(`int8`,取值 0~15),外加 `state` 和 `levels_completed`。**没有** `score` 字段,没有奖励信号,没有"离目标还有多远"。动作叫 ACTION1~7,不告诉你哪个是上、哪个是下。

官方 baseline 给 LLM 的全部背景知识是 321 个字符:

```
# CONTEXT:
You are an agent playing a dynamic game. Your objective is to
WIN and avoid GAME_OVER while minimizing actions.

One action produces one Frame. One Frame is made of one or more sequential
Grids. Each Grid is a matrix size INT<0,63> by INT<0,63> filled with
INT<0,15> values.

# TURN:
Call exactly one action.
```

单帧观测序列化成文本约 8941 字符(≈2235 token),每走一步重发一次。按本方案 335 步算,光观测就是 **748K token** 量级,而这还是已知最优解、不含任何试错。这解释了官方 `FastLLM` 为什么把 `MAX_ACTIONS` 卡在 80。

顺带一提,官方 baseline 里有个 `GuidedLLM`,注释写着 *"with explicit human-provided rules in the user prompt to increase success rate"*,把这个游戏的规则一条条写进了提示词。**官方自己也知道模型摸不出来。**
