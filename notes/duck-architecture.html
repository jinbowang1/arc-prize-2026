一、两层循环：这是 act-look-act，不是 ReAct

solver.play()                                   外层 · 一局游戏, 时间上限 7920s
│
├─ while not should_stop():
│    ├─ analysis_step += 1
│    └─ analyzer.analyze(...)  ──────────────►  内层 · 一个 "轮"
│         │
│         │  while turn_count < tool_steps:          ← 关键: 轮内可以反复
│         │    ├─ messages = [system, *history, user]
│         │    ├─ _trim_messages_for_context()        按 token 预算裁剪
│         │    ├─ _chat_completion()  ─────────────►  一次模型生成
│         │    ├─ 解析 tool_calls
│         │    ├─ _dispatch_tool() → run_sandboxed_python()
│         │    │     └─ 子进程里 exec 模型写的代码
│         │    │          └─ 代码内部可直接 action([...])  ← 动作在代码里
│         │    ├─ 结果 append 进 messages
│         │    └─ if 到 yield_seconds: break          ← 让出闸门
│         │
│         └─ return AnalyzerTurnResult
│
└─ 写状态快照 / 记录 / 下一轮
跟 coding agent 的 ReAct 循环差在哪
ReAct（多数 coding agent）Duck 的 act-look-act
模型输出一个动作 → harness 执行 → 结果回上下文 → 模型再想 模型输出一段代码，代码里可以边走边看边决定
每个动作都要一次完整生成一段代码里能走 N 步（实测最多一轮 49 步）
循环/条件判断由模型用自然语言表达循环/条件判断就是 python 语句
模型写的代码可以长这样，动作、观察、再动作全在一次生成里闭环： 
res = action(['LEFT'])
if res['board_changed']:
    seg = current_frame.segmentation      # 状态已自动刷新
    tgt = [n for n in seg['nodes'] if n['color']=='R']
    action([{'action':'MOUSE','row':tgt[0]['boundary'][0][0],'col':...}])

实证：08-25 同模型同题对照，Duck 2 关 58 步，改成一次一动作的版本 2 关 317 步。差一个量级。

二、模型调用：一次请求怎么拼出来

messages = [
  {role: system, content: 系统提示词}            ← 14187 字符, 每轮重发(靠前缀缓存)
  ...history_messages...                        ← 跨轮保留, 上限 30 个 assistant 轮
  {role: user,   content: 本轮提示 + 棋盘图}      ← 每轮新建
]
        │
        ├─ _trim_messages_for_context()
        │    budget = 32768 - reply_reserve(512) - safety(512)
        │    while 估算 token > budget:
        │        _drop_oldest_history_block()   ← 整块丢最老的, 不砍字符
        │
        ├─ _chat_completion(messages, tools=[python])
        │    temperature 0.6 / top_p 0.95 / top_k 20 / thinking on
        │
        └─ 返回 → 若服务端仍报超长 → 再裁一次重试 → 仍不行才抛
裁剪按"块"而非按字符：保证 assistant + tool_result 成对丢弃，不会留下半截的工具调用。这是长跑 agent 的稳定性细节。

三、工具：只有一个 python，但它很特别

沙箱是什么 
run_sandboxed_python()
 └ tempfile.TemporaryDirectory()
   └ subprocess.Popen([python, -I, -S, -c, BOOTSTRAP])
     ├ stdin/stdout 走 JSON 行协议
     ├ RLIMIT_CPU / FSIZE(1MB) / NOFILE(32)
     └ 跑完 → 进程销毁 + 目录删除

每次工具调用全新子进程。所以模型 def 的函数活不过这一轮 —— 实测 24.6% 的调用含 def。

沙箱里能用什么
注入的变量current_frame previous_frame history transitions valid_actions last_action_result
注入的函数action(actions) ← 真正执行游戏动作
可 import只有 12 个纯计算模块：bisect collections copy fractions functools heapq itertools json math operator random re statistics string
没有os pathlib open — 无法读写文件
action() 的往返：这是整个设计的核心 
沙箱子进程                            宿主 (ToolAgent)                     引擎
 action(['LEFT'])
   └ _send({type:action})  ──────────►  action_handler()
                                          └ step_env()  ──────────────►  真正执行
                                                                          ↓
                                        ◄──────────────────────────────  新状态
                                          _compact_action_result()
     _recv() ◄─────────────────────────  {action_result, state}
   └ _refresh_state()   ← current_frame / history / transitions 全部就地更新
 继续执行下一行 python

所以代码里 action() 之后的那一行，看到的已经是动作执行后的世界。这就是 act-look-act 能成立的机制基础。

四、记忆：三套并存，生命周期各不同

层存什么活多久怎么进上下文
对话历史
_history_messages		过去若干轮的完整消息（含 assistant 推理、工具调用、结果）上限 30 个 assistant 轮，超预算按块丢最老的直接作为 messages 中段
世界模型
_summarized_knowledge		7 个字段：world_model / goal_model / action_model / recent_findings / open_questions / current_plan / cross_level_notes永不丢弃，跨关卡保留每轮渲染进 user 消息
运行时状态
runtime_state.json		当前帧、历史帧、valid_actions每轮覆写，落盘由沙箱读取，不进上下文
世界模型是模型自己写的：它在回复里写 World model: Goal model: Plan: 这类前缀段落，_extract_scientist_note() 把它们抽出来存进字典，下一轮再渲染回提示词。提示词里那句强制要求："BEFORE EXECUTING NEW ACTIONS YOU MUST ALWAYS GIVE THE REVISED VERSION OF THE WORLD MODEL"。

这是 Duck 处理"长跑失忆"的办法 —— 对话历史会被裁掉，但模型自己提炼的结论一直在。

五、让出闸门 yield_seconds：设计意图与我们踩的坑

def control_yield_reason():
    if should_stop(): return "stop_requested"
    if (now - turn_started_at) >= yield_seconds:
        return "turn_time_budget"      ← 到点交还控制权给 solver
    return None

设计意图：让内层循环别陷太久，逼模型频繁交班、频繁产出动作。sonpham 的实验记录说「tempo 机制（60 秒让出、act-look-act）在这个模型尺度上压倒其它一切因素」。

但配 12 tok/s 的模型时它失效了。 线上一次生成要 130~170 秒，而闸门是 60 秒 —— 检查永远发生在生成之后，内层循环实际只跑一次。act-look-act 从未发生。

更糟：模型没吐出工具调用时，harness 会追加提示准备重试，continue 回循环顶部第一件事就撞上闸门 → 重试永远轮不上，那一轮直接作废。
闸门总生成次数总轮数生成/轮说明
60s10619931.07现状，act-look-act 不成立
200s10615651.88
400s10613712.86一轮容得下走-看-再走
900s10611995.33轮数少，纠偏机会也少

按第六发 25 局真实耗时序列模拟（986 个轮间隔，中位 145s、P90 395s）。生成总次数由时间预算决定基本不变，闸门只改变它们如何分组成轮 —— 但同轮内的第 2、3 次生成能命中前缀缓存，省下重发 system prompt 的开销。

六、一句话总结各部分的取舍

设计换来了什么代价
动作写在 python 代码里一次生成能走多步、能写搜索模型必须会写代码
action() 后状态就地刷新act-look-act 闭环成立宿主与沙箱要维持双向协议
沙箱每次全新子进程隔离干净、跑崩不影响宿主模型的辅助函数活不过一轮
历史按块淘汰消息结构永远完整丢弃粒度粗，可能丢掉有用的
世界模型由模型自写自读长跑不失忆，跨关卡保留结论模型写错了就一直错下去
让出闸门逼模型频繁交班必须与模型速度匹配，否则机制失效
