### 关于末行的 `[verify] ... 未通关`

三个 harness 日志末行都是 `[verify] 全新环境重放 N 步: 未通关 — 通关 X/6`。
这不是重放失败。`harness/run.py:302` 的 `verify_replay` 返回值判据是
`obs.level >= obs.win_levels`,即**整个游戏 6 关全通**才记 True;
跑测只跑了前 2~3 关,自然到不了 6/6。

重放本身是对得上的:cd82 重放 11 步(= L1 的 5 步 + L2 的 6 步)后 `通关 2/6`,
r11l 重放 3 步后 `通关 1/6`,与各自跑测声称的关卡数一致。
这一步存在的意义是防分段解拼接时的边界重复(ls20 L6 踩过,见 `verify_replay` docstring)。

### 根因:`perform_action` 只注入,`step()` 才结算 —— 而这是**游戏规则不是 bug**

sc25 上一路排除的假设(每条都有实测,别再重走一遍):

  - 掩码掩掉了游戏区域 -> **否**,掩码掩了 **0 格**
  - 决策帧/动画帧,raw=False 能拿到完成帧 -> **否**,raw=False 也是 0 格,
    且 `is_action_complete` 动作后就是 True
  - 画面滞后一拍 -> **否**,`act` 走 `[A3,A1]` 的结果**逐格等于只走 A1**,A3 整个被丢
  - `get_pixels` 能零成本读到真实画面 -> **否**,它也报 0 格(状态本身没推进)

真相:`perform_action` 把动作放进输入缓冲,引擎的 `step()` 才结算。而**官方 SDK
的 `Environment.step` 内部同样只调 `perform_action`** —— 所以这是这个游戏的规则,
不能靠偷调 `step()` 绕过去,那样算出的解在官方接口下不成立。

### 修法:指纹要正好等于语义状态

走 A3 和走 A1 之后**画面完全相同**(都还是开局),区别只在缓冲里待结算的是谁。
指纹只看画面 -> 全部去重 -> BFS 深度 0 报"队列穷尽"。

`Obs.pending`(待结算动作 id)进指纹,`fork` 一并克隆,`bfs_level_up` 与
`best_first` 四处调用点补齐。**四局在案解回归 4/4 通过** —— pending 对
ls20/tr87/ft09/cd82 只是个恒定多余维度。

🚨这与"指纹不能用整帧像素(会混进计时器)"是同一条原则的两面:
**指纹要正好等于语义状态,多一点(计时器)去重失效,少一点(输入缓冲)去重过头。**

### 表征层同一个 bug:单步 peek 看到的是上一个动作的效果

`Game.detect_lag`(探测这一局是否滞后)+ `Game.effect`(滞后局走两次看真效果)。
**走两次 a 得到的正是 a 的单次真效果**(实测 `viaact(3,3)` 逐格等于 `truth(3)`),
克隆体试探免费,所以不必偷调 `step()`。判定结果:sc25=True,cd82/ls20=False ——
不会误伤已攻的四局(无条件走两次会把"移动一格"看成"移动两格")。

### 关于滞后语义:手工推理连续翻车三次,已停手

`perform_action` 只注入、下一次调用才结算,由此推出的模型我改了三轮都对不上:
"滞后一拍" -> "丢弃首动作" -> "方块是构型" -> 否掉 -> 又确认 -> 仍解释不了
"首点击重复 5 步全变 2"。每次都是拿少量数据过度归纳。

**结论:不再手工推语义,交给搜索**(搜索在 act 语义下天然自洽,每个节点都是真实
clone),判据只认 `level` 上升,不用猜的颜色配对。

⚠️但补了一条必要修正:**过关信号可能也滞后**,所以每扩展一步要多 fork 一次
补步查 level —— 只查当前 `o.level` 会漏掉"最后一步已达标但还没显示"的解。

### 🚨"指纹要正好等于语义状态"今晚撞了四次

  1. 少了**输入缓冲** → 去重过头,BFS 深度 0 假穷尽(sc25 裸跑 1 秒)
  2. 多了**轨道方块的无关变化** → 状态空间炸开,harness 全屏指纹最深只到 5-6 层
  3. 少了**方块状态** → 加了按键动作却没把它们影响的状态进指纹,按键产生的状态
     全被去重掉、方块维度根本没被探索(**我现犯的**,跑了一轮才发现)
  4. cd82 早先那次:整帧像素混进**计时器** → 同一位置在不同步数永不相等,去重失效

多一点去重失效,少一点去重过头。**这条比这一局打到第几关值钱。**

### 🚨顺序实验:两个子系统不可分段 —— sc25 是"构型 x 提交"结构

### ~~新机制:颜色转移依赖构型~~ 🚨**这条是错的,已被干净实验否证(见下)**

同一批枚举里掉出来的:

    中列(色0)点 2 次 -> 回到 0        中列点 3 次 -> 变 2      => 0 <-> 2 切换
    边列(色2)点 1 次 -> 变 14                                  => 2 -> 14

同样是点击,转移规则不同;两组实验的差别只在**到达该位置时按了不同的按键序列**,
也就是**构型不同**。这正是顺序实验定性的"构型 x 提交",只是枚举时没控制它。

**所以"图案 x 位置"这个二维枚举根本不完备** —— 真实状态是 **(画布 x 构型)**,
拿二维格点去覆盖三维空间,漏掉的正是关键维度。
⭐这也说明手工枚举在这一关已经到头了:能正确覆盖 (画布 x 构型) 的恰恰是搜索器
(它的语义指纹就是这两项),继续手工试只会一直漏维度。

### 🚨订正:颜色转移**不依赖构型** —— 上一条结论混杂了两个变量

上一条拿"中列点2次回到0 / 边列点1次变14"断定"转移依赖构型",但那两组实验
**同时**变了两件事:到达位置的按键序列(构型)**和**格子的初始色。只控制了一个。

干净做法:固定构型,只连点同一个格子;再换构型重复同一串:

    构型A(不动) / B(下2) / C(左3) / D(下2左3)
      格(0,0)(初始色2)连点: [14,2,14,2,14,2]   四种构型**完全相同**
      格(0,1)(初始色0)连点: [14,0,14,0,14,0]   四种构型**完全相同**

=> **颜色转移与构型无关**;两格序列不同只是**初始色不同**:
   色 2 的格切换 **2 <-> 14**,色 0 的格切换 **0 <-> 14**。
⚠️顺带修正另一个数:之前读到的"中列 0 <-> 2"也是错的,实际是 **0 <-> 14** ——
那个读数被滞后错位偏移了一拍。

于是画布状态其实是**二值**的(每格 = 初始色 or 14),3^9 塌成 **2^9 = 512**。

### 为什么失败:选区不可靠,而我只验了"建成"没验"建对"

各局切出的画布:

    cd82 (34,43,27,36) ✅ 正是地面真值        ft09 (36,57,36,57)
    sc25 (14,51,20,41) ❌ 正确是 (49,61,24,36)
    r11l (30,32,1,2)   ❌ **3x2 只有 6 格**
    ls20 (40,49,29,48) ❌ 掩到只剩 200 格,搜索直接瞎

**一局对、三局错。** 而我设的"太小就退回"保护写在了**画布+构型的总和**上
(380/484/566 格都通过了),问题却出在**画布本身** —— 保护写在了错误的量上。

🚨**能力接进去 != 能力生效。** 我验证了"掩码建成"(格数都打印了),
没验证"掩码建对"。中间指标与最终指标之间又隔了一层 ——
今晚已经在 prune_noops 上栽过同一跤(中间指标全好、端到端更差)。

### 这次失败换来的正确方向

选区正确才是语义指纹的**前提**。前提不成立时,压缩状态空间不是"没帮助",
而是**有害**(掩掉要害 = 制造假穷尽 = 漏解)。
所以下一步不是继续调掩码,而是先解决**"怎么可靠地认出答案区"** ——
它对应的是 `propose_prompt_answer` 的提议质量,而不是搜索。

### 改进 #5:MoverToAnchor —— **两版都失败,已回退**;但它逼出了正确约束

动机(有依据):`ObjectToObject` 把 mover/anchor 记成**上一关的形状键**,而 ls20 的
L1→L2 小块全变((39,45,13,19)/(40,41,29,33) → (4,4,54,58)/(5,9,8,8)/(31,33,20,22)),
继承来的目标必然被开局体检判"本关定位不到目标对象"。
**关系型的一半在"目标由另一个对象决定",另一半在"参数由当前帧自己取值"** ——
ObjectToObject 只做到前一半。

于是新增 MoverToAnchor:参数只记颜色,mover/anchor 每关从当前帧重新识别。两版都失败:

| 版本 | `_pick` 的规则 | 结果 |
|---|---|---|
| v1 | "面积**最小**的当 mover(可动件通常比场景小)" | 挑中两个 **1×1 碎点**,is_goal 恒假 |
| v2 | "剔掉碎点后取面积**最大**的两块" | 挑中两个**跨半屏巨块**,`is_goal(before)` 就已为真 |

🚨**两版都是在用尺寸猜"谁是可动件",两次都猜错、而且错向相反。**
没有依据的启发式换个游戏一样会错 —— 这跟今晚早些时候"用 h 卡住推断表征缺维度"
是同一类错误:**把推断当依据**。

### 这次失败逼出的正确约束

"谁能动"是**因果信息**,不是尺寸特征。而 `discover` 早就算出来了 ——
每个实体都带 `movers` 字段(哪些动作能移动它,ls20 上给出 5 个 25 格的块)。
问题在于 **`fit` 只拿到 before/after 两帧,拿不到实体信息**。

=> 正确做法不是在 `fit` 里继续猜,而是**让 agent 把已算出的实体(带 movers)
   传给目标拟合**。这是接口问题,不是判据问题。

## 九、sc25 L3 攻不下来:四条路全部实测封死

L1(13 步 vs 人类 36)、L2(5 步 vs 6)已破并经全新环境重放复核。**L3 未破**,
而且不是"再多给点时间"的问题 —— 四种手段各自都有硬记录:

| 手段 | 结果 |
|---|---|
| 盲搜 BFS(32 动作全集) | 扩展 7000、**最深 5 层**;解按人类 32 步推算在 15 步开外 |
| 语义穷尽 | **55188 状态全搜完**,(画布 × 方块位置) 空间内无解 |
| 随机试探 | **4000 条 × 40 步 = 16 万步,一条没撞中** |
| 启发式 | h 46→16;八倍算力 h **3→3 纹丝不动**(目标本身不对) |
| 手工看画面 | 六条否证,**四次读数被滞后骗** |

### 根本障碍:滞后语义没澄清,导致"看画面"这条路系统性失真

`perform_action` 只注入、下次调用才结算 —— 由此我改了**四轮**读数模型,
每轮都能解释部分数据、又被新数据推翻:

    "L1 过关时轨道空了"   -> 错(观察窗太窄,方块在窗外列17-18)
    "中列 0<->2 切换"      -> 错(实为 0->2 后稳定)
    "颜色转移依赖构型"     -> 错(混了构型与初始色两个变量)
    "边列/中列的切换规则"  -> 错(反复点同一格画布纹丝不动)

🚨**只要读数不可靠,我对这一关的任何"理解"都不可信**,而 L3 的过关条件
恰恰需要理解才能构造 —— 盲搜和随机都已证明够不着。

### 停手的依据

项目纪律是"**换搜索策略而数字纹丝不动就该去改表征**"。
而我现在**连表征该改什么都是靠猜**(MoverToAnchor 两版都是用尺寸猜可动件,
错向还相反) —— 那正是该停手的信号:继续投时间的期望产出,
低于把这些否证写清楚。

**sc25 停在 2/6。** 后来者接手时,上面那张表里的每一条都不必重走。

### 🚨再订正:画布**是二值的**,"三值"结论错了 —— 错源是我自己的假 noop

干净重测(逐格连点、直接读该格中心像素):

    初始色 2 的格: [14,2,14,2,14,2]   2 <-> 14 切换
    初始色 0 的格: [14,0,14,0,14,0]   0 <-> 14 切换

**每格只在"初始色"与 14 之间切换 —— 画布是二值的**(最早的判断是对的)。

错源:中间几个实验用了个"noop 补步"动作,而那个 noop 是用 **`effect`(走两次)**
判定出来的 —— 它在**单步**时其实有效果。**用"走两次"判定的 noop 去做单步补步**,
读数自然乱,于是读出"中列变成 2"这种假象,进而推出"画布三值"。

两条连带纠正:
  · **"画布三值"作废**;那次 **55188 状态穷尽的结论重新成立** ——
    (画布 × 方块位置) 空间内确实无解
  · 我此前说"L3 读不明白",其中**相当一部分是自己的诊断 bug 造成的**,
    不该全算在游戏头上

⭐教训:**判定"什么是 noop"用的语义,必须与后面使用它的语义一致**。
这与今晚 ObjectToObject 那次(生成用重叠、判定用同心)是同一个形状:
**同一个概念在两处用了不同判据**。

### 最后一个候选也排除:计数器是**步数条**,与过关无关

    开局 32 格 → 按键 3 次 28 → 6 次 20 → 9 次 16 → 12 次 **16(饱和不动)**
    交替走同样, **与动作类型无关, 只跟步数有关**;单步看不出变化(每几步才掉一格)

🚨与 memory 里 r11l 那条完全同型:*"列0那根条是**步数表不是命条**(11 步填满后
饱和;我曾推断'点错扣命'被自己的测量推翻)"* —— **同一个坑, 换个游戏又踩一次**。

### sc25 L3 收口:候选已穷尽

    画布(2⁹) × 方块位置(30)  → 55188 状态穷尽, **无解**
    全屏帧 diff              → 除画布/方块外**只有计数器**在变
    计数器                   → **步数条**, 饱和后不动, 与过关无关
    盲搜 / 随机              → 最深 6 层 / 16 万步, 都够不着

**过关条件不在任何可观测维度里** —— 要么依赖不可见的内部状态(动作历史/顺序),
要么需要某种没想到的动作组合,而那已超出"从观测反推"能做的范围。

**sc25 最终 2/6**(L1 13 步 vs 人类 36、L2 5 步 vs 6,均经全新环境重放复核)。
