# 计数器的自变量不一定是步数 (2026-08-15, cd82 L3)

一句话: **canvas 卡在"差 12 格"的真凶, 是一个计数器漏进了构型指纹**;
而它漏网的原因是计数器检测默认了"计数器随步数走", 它随的却是**涂了几笔**。

## 一、症状与真凶之间隔了五层

```
probe 漏掉 (63,55)                      <- 真凶
  -> 构型指纹含这一格
  -> 提交动作让它 4->5, 于是"提交改变了构型"
  -> 双底自证 10/10 全被拒 -> 收不到底
  -> 采集判 0/100 格 -> 画笔库瞎
  -> 第 4 笔"没有任何一笔能缩小差异" -> 卡在差 12 格   <- 症状
```

症状那一头看起来是**搜索/规划**问题(找不到摆法), 真凶在**感知**那一头。
中间隔着五层, 每一层看上去都自洽 —— 这是为什么"加宽 beam / 调判据"一路无效。

## 二、抓真凶的那一步

不是靠读代码想出来的, 是靠一个只问机制的诊断跑(`diag_floors.py`):
**在落 3 笔之后的状态, 逐个提交动作打印"答案区之外改了哪些格"**。

```
落 3 笔后:  A5 / A6(34,19) / A6(31,19) / A6(31,21) / A6(31,20)
            答案区内改 0 格 | 答案区外未掩改 1 格
            (63,55): 4 -> 5        <- 五个提交动作全都只改这一格, 同样的变化
关卡开局:   同样的问法 -> 答案区外改 0 格
```

**同一个问题在开局问和在落笔后问, 答案不一样。** 这是关键 —— 只在开局采样
就永远看不见它。

## 三、为什么两道计数器检测都没抓住

- `probe_volatile`(单步判据: 每个动作都改它、且都改成同一个值)
  差一点就抓到了 —— 五个提交动作确实全都把它改成同一个值。
  漏网原因: 它要求**所有**动作都改, 而 32 个调整动作不碰这一格。
- `probe_counters`(跨步判据: 三条等长路径, 同一步取值都相同却随步数变化)
  漏网原因更根本: **(63,55) 承载的不是"走了第几步", 是"涂了第几笔"**。
  三条路径步数相同但涂笔次数不同, 同一步上取值就不同, 判据于是认定它
  "与按了什么有关", 放行。

**判据没写错, 是把计数器的自变量默认成了步数。** 计数器可以挂在任何一类动作
的累计次数上 —— 涂笔数、开火数、拾取数。判据该放宽成:
**存在一个动作子集, 子集内都把它改成同一个值、子集外都不碰它。**
⚠️但这个放宽有误伤前科(cd82 L2: 纯交集法把整片游戏区当计数器掩掉,
BFS 深度 0 就报"状态空间已封闭"), 回流到 probe 前必须单独验。

## 四、落地的修法: 用因果结构而不是统计判据

补丁留在 canvas 层(`_config_mask`), 因为这一层有领域约束兜底, 比纯统计判据安全:

> 骨架那句话("提交只改画布, 调整只改构型")本身就是判据:
> **答案区之外任何被提交动作改动的格子, 按定义就不属于构型。**

不用去认它是什么, 因果结构直接把它划出去。

### 效果(cd82 L3 实测)
| | 第 1 笔 | 第 2 笔 | 第 3 笔 | 第 4 笔 |
|---|---|---|---|---|
| 修前能判 | 65/100 | 30/100 | **0/100** | **0/100** |
| 修后能判 | 65/100 | 30/100 | **30/100** | **10/100** |

**但差异仍然是 12 格, 一格没动。** 按本项目反复应验的判据 ——
换方法而数字纹丝不动 = 表征还缺自由度 —— 说明真凶不止这一个, 于是转去
问"那 12 格到底是什么"(`diag_last12.py`)。下面是问出来的。

## 四之二、真正的地板: 抽象层解到哪, 由采集判到哪决定

### 定量规律(两次独立印证, 一格不差)
| 采集判得动 | 抽象层的地板 |
|---|---|
| 50/100 (28c81c6 当时) | 最好差 **50** 格 |
| 90/100 (本轮定向造底后) | 最好差 **10** 格 |

**地板 = 判不了的格数。** 不是搜索不够强, beam 宽 300 深 8 与此无关。

### 为什么早先看不到这条规律
`Brush.apply` 把"采集判不了"默默当成了"这一笔不覆盖它"。于是抽象层能算出
一条 65->55->12->**0** 的完美方案 —— 最后一步是**凭空变出来的**,
execute 逐笔翻译回真机时才发现"第 4 笔找不到摆法"。

修法: 加 `UNKNOWN = -1`, 没证据的格涂成 UNKNOWN, 它和任何目标色都不等。
抽象层于是只有两种结局, 两种都比撒谎好:
  - 找到**处处有证据**的方案 -> 真机上一定存在
  - 诚实报"未解出(最好差 10)" -> 直接指出该去补采集哪一块

**"漏解可以, 错解不行"在抽象层的同一句话。**

## 四之三、可判性地图: 造底必须定向, 不能均摊

cd82 L3 开局的可判性地图是一条**完美的水平分界线**:

```
o o o o o o o o o o      行 0-4 全部可判
...
. . . . . . . . . .      行 5-9 一格都判不了
```

而判不了的那 50 格**全都被改变过**(够不着的 0 格) —— **缺的不是笔, 是"去涂那里的底"**。

- 均摊挑 anchor(随便取几个调整动作): 50 -> 65, 换三种造底方式**纹丝不动**
- 定向挑 anchor(用现有库里覆盖"判不了区域"最多的笔的调整序列): 50 -> **90**

这就是老教训"**frontier 导向的定向探索, 而不是均摊**"在采集层的同一句话。
⚠️用来挑 anchor 的那些 covered 本身还不可靠 —— 但**拿来排序够用了**,
这是"模型当排序器和当预测器是两条不同及格线"的又一次应用。

### 造底的三种手段与各自的死法
| 手段 | 死法 |
|---|---|
| 在当前构型直接提交 | 刚涂完的再涂一次是**幂等**的, 所有底一模一样 |
| 去别的构型涂一笔再走回来 | 要求构型可逆 |
| **沿同一条轨迹走, 中途提交与否不同** | 两样都不要, 只依赖"提交不改构型" |

第三种是本轮新增(`_trajectory_floors`)。它只需要一条已验事实: 提交不改构型,
所以两条轨迹的调整序列逐步相同 -> 终点构型必然相同, 而中途涂没涂让画布不同。

## 四之四、最后卡住的地方: 根本没有一张静态的构型图

把证据补满(单笔盲区全部为 0、跨轮零冲突)之后, 抽象层解出 4 笔, 翻译回真机
仍然失败 —— 但错误换了一个: **"第 2 笔: 构型图上走不到这支笔的构型"**。

`execute` 原本用"在真机上 BFS 搜一支能涂出目标画布的笔"来翻译, 这掩盖了一个 bug:
**画笔库里每支笔的 `seq` 都是从"采集时那个根构型"出发的**, 连着用两支笔时第二支
的 seq 从根走没有意义。改成 `execute_cfg`(按 `Brush.cfg` 在构型图上找路)之后,
真正的问题才露出来。

### 一个逻辑上不该出现的矛盾
```
从当前构型 BFS:      56 个(穷尽)
从 anchor 终点 BFS: 190 个(穷尽)
交集 37 | 只在 A 19 | 只在 B 153
```
anchor 是**从 A 走过去的**。静态图上, A 能到 anchor 终点 => anchor 终点的可达集
⊆ A 的可达集 => 190 ≤ 56。实测反过来, 而且 A 还有 19 个 B 到不了的。

**唯一的解释: 动作效果依赖状态。** anchor 里那个 `A6(25,4)` 是坐标固定的点击,
走到别处画面变了, 同一个坐标点的是别的东西。所以根本不存在一张静态构型图,
而我的 BFS 从头到尾用的是**关卡开局算出来的那份动作表**。

这是"动作候选必须随状态动态重算"的**第七次**, 犯在 BFS 内部;
也和 r11l L2 的诊断("每个点击的效果都取决于别的东西的状态")是同一个结构。

### 下一步(未做)
- 采集与找路的 BFS 都要**逐节点重算动作表**(至少把各轮见过的新点击目标并进去)
- 规划要**在构型图上做**: 状态 = (构型, 画布), 而不是把画笔当无序集合随便挑

## 五、两个被自己推翻的中间结论(留着当教训)

1. **"构型图不强连通, 落 3 笔后走不回开局构型"** —— 当时那个证据是坏的:
   (63,55) 一变所有指纹全变, "重合 0 个"只说明**认不出**, 不说明回不去。
   ⚠️但后来用干净指纹重测, **走不通这件事本身是真的**(见四之四)。
   **结论碰巧对, 当时的证据却不支持它** —— 这种情况比结论错更危险, 因为
   它会让人以为那套推理方法是可靠的。判据坏了就是坏了, 跟结论对不对无关。
2. **"落笔后答案区外差异 292 格是构型的正常变化"** —— 那个数字里混着计数器,
   不能当证据用。

## 六、"采样只在一个状态上做"第五、第六次

前四次: 搜索候选表 / 槽搜索固定动作表 / 可变格只在开局采 / 动作二分只在开局做。

- **第五次**: canvas 的骨架前提"提交不改构型"我只在关卡开局验了 60/60,
  就当成了全局事实。落 3 笔之后它是 **0/10**。而这条前提是整个 canvas
  方法的地基 —— 地基是在一个状态上验的。
- **第六次**: 修的时候我自己又犯 —— 只在"落 3 笔"这一个状态测提交动作改了哪些格,
  手工补掩 (63,55) 后重跑, 结果仍是 0/100, 因为污染格不止一个。
  所以 `_config_mask` 必须**摊开到多个构型上问**。

写下这条时代码注释里已经有前四次的警告了, 我一边读着它一边犯了第五次。
**光把教训写进注释不管用 —— 判据得写进代码里, 让它自己在多个状态上采。**
