## 四、六个通用缺陷(换游戏会复现,所以逐条记)

### 1. 动作空间写死

`run.py` 里是 `action_space([1,2,3,4,5,6])`。r11l 的 `available_actions=[6]`,
于是去试 5 个不存在的键。**动作空间只能问引擎。**

### 2. `probe_inverses` 按动作 id 传参

有效动作全是带坐标的点击时,`[a.id for a in live]` 全是 6,再 `Action.key(6)`
造出一个**没有坐标载荷的"点击"** —— 探的根本不是同一件事。
**动作空间不能靠 id 反推,只能拿动作对象本身走。**

### 3. 实体发现的合并判据是错的

旧判据"变化区有重叠就合并"。r11l 每次点击重绘一大片,所有动作两两重叠,
一路并到底,报出**一个 396 格、bbox 覆盖整屏的"实体"** ——
等于什么都没发现,而且没发现得很像发现了。

新判据:**总是一起变的格子才是同一个实体**(给每格算"会改动它的动作集合"当
签名,签名相同的归一组)。拿 cd82 回归——它正是这个函数的原始动机:

```
17x24 @ (21,37,14,37) 102格 受1个动作影响 ['A3']     ← 大面板
17x24 @ (21,37,26,49) 102格 受1个动作影响 ['A4']     ← 另一个面板
 5x10 @ (34,38,27,36)  50格 受1个动作影响 ['A5']     ← 那支 50 格大笔
```

**当年卡我几小时的那个漏掉的小面板,现在是自动登记的。**

### 4. 🚨计数器检测漏掉"每几步才掉一格"的资源条

这条是本轮最硬的产出。

`probe_volatile` 的判据是**单步**的:"每个动作都改它、且都改成同一个值"。
它抓得住每步跳动的步数显示,抓不住**每走几步才掉一格的资源条**。
r11l 列 0 那根竖条,只有顶端 (0,0) 每步都变被抓到,(1,0) 往下全逃掉了。

后果不是"少掩几格"这么轻:抽象模型层里每个动作都带着 3 个"冲突格",
**220 格一致的覆盖表被这 3 格一票否决**,可用动作数 = 0。

补的跨步判据是同一条原则往时间轴上的延伸——**变成什么与按了什么无关**:
走三条互不相同的等长路径,在每一步比对,处处相同却又随步数变化的格子,
承载的信息只有"第几步"。

效果:

| | 掩掉的格子 | 模型可用动作 |
|---|---|---|
| r11l 只用单步判据 | 1 格 | 0 / 38 |
| r11l 加跨步判据 | **9 格(整根竖条)** | **23 / 38** |
| cd82 只用单步判据 | 1 格 | — |
| cd82 加跨步判据 | **6 格**(右下角 (63,59)~(63,63) 一根之前完全没发现的计数器) | — |

误伤风险实测过(cd82 L2 曾被纯交集法整片误掩,BFS 深度 0 就报无解),所以
用三条路径而不是一条,并要求该格确实随步数变过。**cd82 回归:L1 5 步、
L2 6 步,与记录在案的成绩逐关一致,没误伤。**

### 5. 假设引擎:重复项 + 参数是上一关的常数

接上假设引擎后第一次跑,L1 通关后拟合出 24 条假设全部"通过梯度检验",
排在第一的是 `color_count(色 0 的格数达到 74)`。三条这样的常数型假设在 L2 上
白烧了九分钟。两个病因:

- **没去重**:24 条里有 **21 条一模一样**的 `object_reach(...(19,41))`,
  挤占"只试前 N 条"的预算,看起来试了很多条,其实反复在试同一条。
- **参数是上一关抄来的常数**:hypo 模块开头自己写着"目标假设必须是关系型的,
  不能是绝对坐标",但注册表里一半是绝对型的,还靠族名字母序排到前面
  (`color_count` 的 c 排在 `object_reach` 的 o 前面)。

改法:去重;新增关系型族 **`color_count_match`(色 A 的格数要等于色 B 的格数)**,
参数由当前帧自己取值;排序改成"关系型优先,然后按证据强度(在已通关的解上
最多下降了多大比例),最后才是族名";绝对型假设在报告里显式标注。

改后 L1 的候选从 24 条降到 6 条,排第一的是
`color_count_match(色 1 = 色 15)`(证据 100%,L1 上 17→0)。

还加了一道**开局体检**:上一关学来的假设,在新关卡开局如果 h 已经是 0 或者
定位不到目标对象,直接淘汰不试 —— 这是 cd82 L3 的原样翻版(起始 h 就是 0,
最佳优先当场退化成广度优先)。

### 6. "空模型"和"假验证"两种自欺

抽象模型层第一次跑,r11l L2 报**可用动作 25 个**,抽象搜索却在展开第 1 个
节点后就堆穷尽 —— 那 25 个全是 noop,空覆盖表"完美一致"。**空模型不算可用。**

另一个更隐蔽的:`support` 记的是采样次数。如果游走走的全是 noop,4 个"状态"
其实是同一个,那就是把一个样本数了四遍,然后管它叫"验证通过"。
现在 support 记的是**互不相同的**状态数,采不出两个不同状态就交白卷。
(r11l L1 实测 4 个状态相差 110+ 格,是真的不同,这条是防御性的。)

## 五、抽象模型层(`harness/model.py`)

动机是速度:真机每扩展一个节点要 fork 一批克隆体,r11l 实测 **8 次扩展/秒**,
BFS 90 秒只推到第 3 层。cd82 定案里那句"真机负责走得通不通、离线模型负责
该往哪走"在这里第三次应验。

学的是**最简偏置:动作 a 的效果是一张固定的"格→色"覆盖表**。
采样判据看**结果值**不看变化量 —— 这是 cd82 "画笔必须双底采集" 的一般化:
拿 diff 当效果,本来就是那个色的格子会被漏掉(当年一笔被记成覆盖 12 格,
真身是覆盖 50+ 格擦掉 38 格);改成"同一个动作在若干不同状态下采样,
每次结果都是同一个值"就自然消解了,连专门铺两种底色都不用。

### 结果(诚实版)

| 游戏 | 可用 | 状态相关 | 无效果 |
|---|---|---|---|
| r11l L1 | **23**(最大覆盖 220 格) | 10 | 5 |
| r11l L2 | **0** | 45 | 25 |
| cd82 L1 | **0** | 8 | 12 |

cd82 全军覆没是对的:它的面板移动和盖印本来就是状态相关的,当年能建起画笔库
靠的是双底采集加答案区语义,不是通用偏置。**判据能把它挡住,说明判据有效。**

## 六、L2 为什么退化 —— 这才是下一步的题目

L1 上 23 个动作能建成常量表,L2 上 0 个。同一个游戏机制不会突变,而采样
状态确实互不相同(排除了假验证),所以这是真的机制差别。

冲突格的分布给了线索:L2 上每个点击的冲突散布在 (4..30, 1..51) 一大片,
**每个点击的效果都取决于别的东西的状态**。

这和 **cd82 的"两个面板"是同一类结构**:显示区由多个选择器共同决定,
单个动作只设定其中一个,所以单看一个动作的效果就"与状态有关"。
常量覆盖表这个偏置表达不了组合。

**下一步该做的是分解式模型**(状态 = 若干个选择器各自选了什么,画面 = 组合的
函数),而不是把抽象层的搜索加宽——这正是那条判据的又一次适用:
*换搜索策略而结论数字纹丝不动,八成是表征缺了自由度。*
